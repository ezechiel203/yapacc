yapacc undo

yapacc undo takes the last package transaction back. It reads the last transaction from the native log, works out its reverse, shows you the plan and the exact command, and asks before doing anything. On apt the plan includes apt's own simulation of the reverse; on dnf it is dnf's own description of the transaction.

It works on pacman, apt, dnf and zypper. On apk, xbps and FreeBSD's pkg it says that undo is not available there.

That is the plan for taking back an upgrade of two packages on Debian 13. A whole system upgrade is undone the same way. This one was a yapacc upgrade of 24 packages and a new kernel, taken back for real on a virtual machine:

The last line is a check. When the native command has returned, yapacc reads the installed versions again and compares them with the plan.

What "undo" means§

The transaction did thisUndo does this
installed a packageremoves it
removed a packageinstalls that version again
upgraded a packagerestores the previous version
downgraded a packagerestores the newer version

Undo acts on one transaction: the most recent one in the native log. An undo is itself a transaction, and timeline shows it like any other.

Important

Undo restores package versions. It does not restore configuration files, databases or anything a package script changed. Only a filesystem snapshot does that; see snapshots. The output repeats this every time.

Where old versions come from§

To restore a previous version, yapacc has to find that exact version. It looks in this order and tells you, per package, where it found it:

Package managerSources, in orderVerification
pacmanthe pacman cache, then the Arch Linux Archivethe archive's detached signature, verified with pacman-key before the package is installed
apt on Debianthe configured repositories, the apt cache, then snapshot.debian.orgrepositories: apt's own; snapshot.debian.org: checked against the recorded hash, not signature-verified
apt on Ubuntuthe configured repositories, the apt cache, then Launchpadrepositories: apt's own; Launchpad downloads are not verified, and the output says so
dnfthe enabled repositories, through dnf's own history undodnf's own
zypperthe configured repositories onlyzypper's own

All or nothing. If one old version cannot be found anywhere, the whole undo is refused (exit code 3) and nothing is changed. yapacc does not apply half of an undo.

On dnf, the old versions are checked for availability before the gate, so a refusal comes from the dry run and not from the middle of the real one. On zypper there is no archive to fall back on: on a rolling distribution such as Tumbleweed, the repositories drop old versions quickly, and an undo of an upgrade more than a day or two old is usually refused for that reason.

A dry run downloads nothing: it asks the archive whether the file exists and reports where each version would come from, with its size when the archive gives one. The real run downloads after you have agreed, into a private directory under ~/.cache/yapacc/undo that is deleted when the undo ends. On apt, when files have to be downloaded, you are asked twice: once before the download, and once more with apt's simulation of the restore in front of you. --yes answers both.

An archive that does not answer is not an archive that lacks the version. A lookup waits 20 seconds for the connection and 60 in all, and is tried twice. If there is still no answer the undo is refused (exit code 3) with "did not answer … so it is not known whether it has that version", and you try again later. Only an archive that answered "no" produces "is in no local cache and no configured repository, and the archive of this distribution … does not have it".

On zypper the same care applies to the repositories: without repository metadata on disk, yapacc cannot know whether a repository still has the old version, says so, and refuses. zypper refresh first.

After the command ran§

The last lines sayWhat happened
Verified: N of N package(s) are at the planned state.the undo is complete
The package versions were restored (N of N verified), but apt reported an error …every version is back, and the native manager still ended with an error, often a package script that failed. Read its output above; exit code 1
K of N package(s) are not at the planned state: …the native command failed part of the way, or reported success and left a difference. The packages are named; yapacc timeline shows the current state; exit code 1

Guards§

Undo refuses rather than doing something it cannot stand behind.

  • The running kernel. An undo that would remove the kernel the machine is running on is refused until you have rebooted into another kernel.
  • Packages that something else needs. If removing a package would break a package installed since, the native manager's dependency check refuses it and yapacc stops.
  • Failed verification. A file from the Arch Linux Archive without a signature that verifies, or a file from snapshot.debian.org whose hash does not match, is deleted and the undo stops with exit code 5.
  • More than was planned. On apt, if the simulation shows that the undo would also remove a package that was not part of the transaction, the undo is refused.
  • Unknown history on zypper. libzypp records an upgrade as an install of the new version, so for a package with no earlier record yapacc cannot tell "new dependency" from "upgraded". When undoing a whole zypper up or dup, it names those packages and asks at the terminal whether to remove them. --yes, --script and a pipe do not answer that question: without a terminal the undo is refused.

Privileges§

Reading the last transaction may itself need root: openSUSE keeps /var/log/zypp/history readable by root only, so there you run sudo yapacc undo. Elsewhere, run it as yourself; yapacc calls sudo or doas for the one command that changes the system.

Options§

OptionEffect
--dryrunshow the last transaction and the plan; download and apply nothing
--yesapply without the [y/N] question

Without either, undo shows the plan and asks. See the gate.

With [safety] snapshot set, a snapshot is taken after you consent and before the first package is touched, as for any other change.

On dnf the plan names the transaction by its ID, and that ID is what is undone, even if another transaction has been committed since you read the plan. On Debian and Ubuntu, multiarch packages are shown and handled with their architecture (libfoo:i386).

Limits§

  • One transaction, the last one. There is no "undo the last three" and no undo of a transaction further back.
  • A restored package is upgraded again by the next full upgrade unless you hold it yourself (IgnorePkg in pacman.conf, apt-mark hold, a dnf or zypper lock).
  • Undoing an install removes the package and does not purge it. On apt its configuration files stay, as after any apt-get remove (state rc in dpkg -l).
  • apt does not remove a package it counts as essential under -y, and yapacc does not override that, with one exception: packages of a foreign architecture that the transaction itself installed. An undo that would need more is refused, and the message says which package.
  • No undo on apk, xbps or pkg.
  • It has been run end to end on booted virtual machines of Arch, Debian 13, Ubuntu 24.04, Fedora 45, Rocky Linux 9.9, openSUSE Leap 16.1 and Tumbleweed, including kernel upgrades followed by a real reboot. It has not been run on real hardware. What works where has the detail.
