Scripting: JSON and exit codes

yapacc is meant to be usable from scripts without parsing prose. Two things make that possible: read commands can print JSON, and the exit code says what kind of outcome it was.

Exit codes§

CodeNameMeaning
0okthe command did what was asked
1failedthe operation ran and failed
2usagebad arguments, or a configuration file that does not parse
3refuseda gate or a guard said no; nothing was changed
4not foundthe package, record or plan does not exist
5integritya hash, signature or chain check failed
6unavailablesomething the command needs is not available: a tool or an optional component that is not installed, a file this user may not read, a feature this build lacks, or a command that does not exist for this package manager

The message goes to standard error as error: ….

The codes that matter most in a script are 3 and 6. A 3 means the system is exactly as it was, by decision. A 6 means the machine lacks something, and the message names it.

Never waiting for input§

--script promises that yapacc never prompts. A command that would have asked [y/N] is refused unless --yes or --dryrun is given, and a privilege tool that would have asked for a password is called in its non-interactive mode and fails at once.

Without --script, yapacc still never reads an answer from a pipe: standard input that is not a terminal cannot confirm anything.

JSON§

--json is a global option and goes before the command:

These commands have a JSON form on every system: why, timeline, briefing, clean, restart, configs, doctor, platform, list, info, search, check, inspect owns, inspect files, inspect orphans, names, get --explain, snapshot list, config, capabilities, and the ledger reads. yapacc docs json prints the complete list, including the Arch-only ones.

A command with no JSON form prints nothing and exits with code 2 ("no JSON output for this command"). It never prints prose with a success status, so a script cannot mistake one for the other.

Fields are only ever added. Treat a key you do not know as ignorable, and do not depend on the order of keys.

An empty answer is an empty array. In text mode the same answer is one line in parentheses, such as "(no orphan: every package installed as a dependency is still needed)", so that a blank screen never has to be interpreted.

What a command has to add in words (a source it could not read, "no repository metadata on disk") goes to standard error as note: … lines. Standard output holds the JSON alone, so yapacc --json check | jq works on a machine that has never refreshed: the array is empty and the note says why.

A few shapes that are useful to know:

CommandShape
platformone object; native_pkg_manager is "pacman", "apt", "dnf", "zypper", "apk", "xbps" or "pkg"; package_logs_unreadable lists the logs that exist and that this user may not read, and is left out when there is none
why NAMEone object; native.manager, native.reason, native.required_by[], native.base, and orphan (true, false or null)
timelinearray of {ts, source, action, name, old_version, new_version}; ts is Unix seconds
doctorarray of {name, state, detail}; state is ok, warn, fail or n/a
cleanarray of {what, size_bytes, count, safety, command, detail[]}
listarray of {name, version, description, …}
checkarray of {name, old_version, new_version, repo} on every package manager; on apt repo holds every origin, separated by ", "; on pacman it is "" for a repository update and "aur" for an AUR update

The shapes of info and inspect orphans differ between pacman and the other package managers; yapacc docs json describes both.
